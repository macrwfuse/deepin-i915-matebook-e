# Deepin 25.3.0 i915.ko for Huawei MateBook E 2022

Rebuilds `drivers/gpu/drm/i915` for Deepin 25.3.0
(`6.18.56-amd64-desktop-rolling`) on GitHub Actions, without a Deepin install.

Deepin ships `CONFIG_DRM_I915=m` and no public kernel source, so replacing the
single module `i915.ko` is the lowest-risk way to patch the display code.

## What the build proves

`scripts/build.sh` refuses to produce a module unless `tools/verify-module.py`
confirms, against the module Deepin actually shipped:

| check | source of truth |
|---|---|
| vermagic byte-identical | `abi/*.json` + `include/config/kernel.release` |
| `depends=` identical | `abi/*.json` |
| `retpoline` identical | `abi/*.json` |
| 42 exported symbol CRCs | recomputed by Deepin's own `gendwarfksyms`, compared to `abi/*.json` |
| 1247 undefined symbol CRCs | Deepin's `Module.symvers` |

`abi/i915-6.18.56-amd64-desktop-rolling.json` is a fingerprint of
`i915.ko` extracted from
`linux-image-6.18.56-amd64-desktop-rolling_25.01.01.40_amd64.deb`
(sha256 `db4fe5a5…`). It is generated by `tools/emit-abi-fixture.py` and exists
because a CI runner has no Deepin module to diff against. If a CRC differs, the
build fails instead of shipping a module the kernel would refuse to load.

### The one intentional difference: `intree`

The build uses `M=` (external module), so modpost is invoked with `-e` and does
not emit `MODULE_INFO(intree,"Y")`. The loader then adds `TAINT_OOT_MODULE`.
That is metadata, not ABI. The module is unsigned either way, which already adds
`TAINT_UNSIGNED_MODULE` — `MODULE_SIG_FORCE` is not set in Deepin's config.

Consequence: the module carries no `.BTF` section, because `pahole -J` needs a
`vmlinux` (which would mean a full kernel build). `CONFIG_DEBUG_INFO_BTF_MODULES`
only affects `bpftool`-style introspection of module types; `btf_module_notify()`
skips modules with `btf_data_size == 0`.

## Layout

```
patches/      0001 native MIPI GPIO bypass, 0002 no DSB for DSI,
              0003 Deepin's 3-argument pci_resize_resource()
abi/          ABI fingerprint of Deepin's shipped i915.ko
tools/        verify-module.py, emit-abi-fixture.py
scripts/      build.sh (CI), install-i915.sh (on-device)
.github/      the workflow
```

Inputs, both pinned by sha256 in the workflow:

- upstream `linux-6.18.56.tar.xz` from cdn.kernel.org
- `linux-headers-6.18.56-amd64-desktop-rolling_25.01.01.40_amd64.deb` from
  `cdn-community-packages.deepin.com`

The headers package is used as `KDIR`. It carries `.config`, `Module.symvers`,
`include/generated/*`, `arch/x86/include/generated/*` and the prebuilt
`modpost` / `objtool` / `gendwarfksyms` / `resolve_btfids` / `fixdep` /
`sign-file` binaries that Deepin itself built with. `scripts/Makefile.build`,
`Makefile.lib`, `Makefile.modpost`, `Makefile.modfinal` and `Kbuild.include` in
that package are byte-identical to upstream v6.18.56, so nothing is hidden, and
no `make prepare` (or full kernel build) is needed.

gcc: Deepin used `gcc 12.3.0-17deepin12`. Ubuntu noble's `gcc-12` has since
moved to `12.4.0-2ubuntu1~24.04.1`, so the workflow installs Deepin's own
`.deb`s (`gcc-12`, `cpp-12`, `libgcc-12-dev`, `gcc-12-base`, sha256-pinned)
over the runner's `/usr`. They only need glibc ≤ 2.38 and noble has 2.39.

This matters because `gendwarfksyms` derives exported-symbol CRCs from the
DWARF the compiler emits: the compiler is part of the ABI. With the exact
compiler installed, `gcc-12 --version` prints exactly the `CONFIG_CC_VERSION_TEXT`
string from Deepin's `.config`, so kbuild does not even emit the "compiler
differs" warning. If a CRC still differs, `verify-module.py` fails the build
instead of shipping a module the kernel would refuse to load — that is the
point of comparing against the fingerprint rather than trusting it.

binutils stays Ubuntu's (2.42 vs Deepin's 2.41). It is only used to assemble
and link; neither the vermagic nor the type DWARF depends on it.

## Using the artifact

Download `deepin-i915-6.18.56-amd64-desktop-rolling` from the run, then on the
Deepin machine:

```bash
sudo ./scripts/install-i915.sh i915.ko.zst
```

It backs up the original as `i915.ko.zst.orig-25.3.0`, installs through
`deepin-immutable-ctl admin exec`, then runs `depmod` and `update-initramfs`.
Reboot afterwards. Rollback is printed at the end; no reinstall needed.

Verify after boot:

```bash
dmesg | grep -i 'Not touching native DSI GPIOs'
dmesg | grep -i 'DSB not used for DSI output'
cat /sys/module/i915/parameters/dsi_native_gpio_bypass   # -1 = auto (DMI match)
```

Secure Boot must be off: `LOCK_DOWN_IN_EFI_SECURE_BOOT=y` rejects unsigned
modules under lockdown.

## The three patches

`0001` — in `mipi_exec_gpio()`, skip the native MIPI GPIO sequence when DMI
matches `HUAWEI` + `DRC-WXX` (or `MateBook E*`). The firmware already powered
the panel; driving HPD / PP_CONTROL again desynchronises it and tears the image.
Module parameter `i915.dsi_native_gpio_bypass`: `-1` auto (default), `0` never,
`1` always.

`0002` — `intel_dsb_prepare()` returns NULL for DSI CRTCs, forcing plain MMIO.
Since 6.13 (`45c548642b56`) DSB is used for plane/color too, so on 6.18 this is
expected to matter.

`0003` — not a fix: Deepin's tree is not pristine upstream. Their 6.18.56
headers export `pci_resize_resource(struct pci_dev *, int, int)` and keep the
four-argument variant as `__pci_resize_resource()`. Blob-for-blob, Deepin's
`drivers/gpu/drm/i915` differs from upstream v6.18.56 in exactly one file,
`gt/intel_region_lmem.c`, for this reason. Patch 0003 makes the extracted
tree byte-identical to what Deepin actually compiled (verified against
`deepin-community/kernel` tag `v25.01.01.41-v6.18.56`).

Also non-patch plumbing: the four in-tree trace headers pin
`TRACE_INCLUDE_PATH ../../drivers/gpu/drm/i915[...]`, resolved relative to
`<KDIR>/include/trace`. Headers packages have no `drivers/`, so `build.sh`
symlinks `<KDIR>/drivers/gpu/drm/i915` at the extracted sources before
building. `-I` cannot fix this (the path is parent-relative), and the header
content is untouched, so the DWARF — and every CRC — is unaffected.

All patches apply with `patch -p1` from the source root.
